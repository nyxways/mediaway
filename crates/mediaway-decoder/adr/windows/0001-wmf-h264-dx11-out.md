# ADR-0001: WMF H.264 DX11 Zero-Copy decode output

- **Status**: Accepted
- **Date**: 2026-07-28
- **Deciders**: @dev-nyxie (+ agent)
- **Crate**: `mediaway-decoder-windows`

## Context

Stage 1 Windows decode needs Media Foundation for H.264 and DXGI textures for Zero-Copy output into callers' D3D11 pipelines. The facade traits are fixed in `mediaway-decoder`. This crate owns `unsafe` MF/DX calls.

Encode-side Zero-Copy uses `MFCreateDXGISurfaceBuffer` for **input**. Decode uses the same DXGI device manager for **output**: hardware decoder MFTs deliver `IMFSample` buffers backed by DXGI surfaces.

## Decision

> When [`VideoOutputPreference::ZeroCopyGpu`](../../mediaway-decoder/src/video.rs):
>
> 1. Require `VideoDecoderConfig::d3d11_device` (opaque `ID3D11Device*`).
> 2. Enumerate a **hardware** H.264 decoder MFT (`MFTEnumEx` + `MFT_ENUM_FLAG_HARDWARE`, H.264 in, NV12 out).
> 3. Bind `MFCreateDXGIDeviceManager` / `ResetDevice` / `MFT_MESSAGE_SET_D3D_MANAGER`.
> 4. Unlock async MFTs (`MF_TRANSFORM_ASYNC_UNLOCK`) and drive `IMFMediaEventGenerator` credits.
> 5. On `ProcessOutput`, query `IMFDXGIBuffer` → `ID3D11Texture2D` — **never** silent GPU→CPU readback.
> 6. Keep the output `IMFSample` + texture COM-alive until the next `push_packet`, `poll_frame` (that returns a frame), or `flush` recycles the surface.
>
> [`VideoOutputPreference::CpuFramesOk`](../../mediaway-decoder/src/video.rs):
>
> 1. Enumerate a **software** (synchronous) H.264 decoder MFT (`MFTEnumEx` +
>    `MFT_ENUM_FLAG_SYNCMFT`, H.264 in, NV12 out) — no `ID3D11Device`, no DXGI device
>    manager, `gpu_device` may be `None`.
> 2. Reject (`DecodeError::Unsupported`) if the selected MFT unexpectedly reports
>    `MF_TRANSFORM_ASYNC` — the CPU path drives `ProcessInput`/`ProcessOutput` synchronously
>    and does not implement the `IMFMediaEventGenerator` pump the DX11 path uses.
> 3. On `ProcessOutput`, copy NV12 planes directly out of the MFT's system-memory output
>    buffer into an owned `Bytes` (`IMF2DBuffer::Lock2D` when the buffer supports it, for
>    stride-aware copy; plain `IMFMediaBuffer::Lock` fallback otherwise) — **there is no GPU
>    texture in this path**, so this is honest CPU decode, not a GPU→CPU readback.

Extradata: best-effort `MF_MT_MPEG_SEQUENCE_HEADER` on the input type when `extra_data` is non-empty (both paths). Verified against real encoded bytes via `tests/cpu_roundtrip.rs` (encodes through `mediaway-encoder-windows`'s CPU-upload H.264 path, decodes through this crate's CPU path, no mux/demux involved — payload and `extra_data` are already Annex-B in that scenario).

**Annex-B / AVCC policy (resolved for demuxer-sourced streams):** when `extra_data` is a demuxed `AVCDecoderConfigurationRecord` (`avcC` box payload — detected via `iso_bmff::bitstream::avc::parse_avc_decoder_config`), `open_dx11`/`open_cpu` convert it to an Annex-B sequence header (`annex_b_sequence_header`) before configuring the MFT's input type, and every pushed `Packet` is converted from AVCC length-prefixed NALs to Annex-B (`avcc_payload_to_annex_b`, using the record's `nal_length_size`) before being wrapped in an `IMFSample`. Annex-B input (e.g. an encoder's own `extra_data`/packets, never muxed) is detected and passed through unchanged — no behavior change for `tests/cpu_roundtrip.rs`. Verified end-to-end via `mediaway`'s `tests/trim_and_splice_windows.rs`: encode → mux (fMP4) → demux → **this** decode path → trim/splice → re-encode → mux → demux → decode again, asserting real per-frame content survives.

## Alternatives Considered

| Alternative | Why not |
|-------------|---------|
| Readback DXGI → CPU NV12 in Zero-Copy mode | Silent/slow; violates ADR-0006 |
| Software MFT + DXGI output | HW path is the Zero-Copy contract for Stage 1 |
| Device inferred only from first output texture | `SET_D3D_MANAGER` must precede streaming |
| HW decoder MFT + DXGI, readback for `CpuFramesOk` | Would need a GPU device even when the caller only wants CPU frames; the in-box software MFT needs none |

Software H.264 decoder MFT was chosen for `CpuFramesOk` over "HW MFT + readback" specifically so CPU-only callers never need an `ID3D11Device` at all.

## Consequences

### Positive

- Honest Zero-Copy decode out; matches encoder DX11 device-manager pattern
- CPU path needs no GPU/device manager at all — works on any Windows machine with the
  in-box software H.264 decoder MFT

### Negative / Trade-offs

- Needs a HW decoder MFT on the machine; otherwise Zero-Copy open fails
- Async event pump adds complexity (Zero-Copy path only — CPU path assumes a synchronous MFT)
- AVCC→Annex-B conversion adds a per-packet copy when the source is demuxer-sourced
  (never Zero-Copy on that path anyway — CPU-side bitstream reframing, not a payload
  format this crate controls); no-op (existing behavior) for Annex-B input
