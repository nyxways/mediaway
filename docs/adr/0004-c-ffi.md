# ADR-0004: C-FFI surface for non-Rust languages

- **Status**: Accepted
- **Date**: 2026-07-27
- **Deciders**: @dev-nyxie (+ agent)

## Context

Mediaway targets multiple app ecosystems (native tools, game engines, managed languages). A documented **C ABI** is the usual interop spine without per-language bindings in-tree on day one.

A single fat `mediaway-ffi` linking every capability would drag large graphs into hosts that only need mux/demux, fighting ADR-0003. FFI must not weaken the permissive license graph, first-class Rust APIs, or Zero-Copy reachability.

## Decision

> Expose C ABI via **per-capability FFI crates** (`mediaway-<capability>-ffi`). Optionally provide umbrella `mediaway-ffi` whose **Cargo features** pull only selected `-ffi` crates. Rust remains primary; FFI is a thin edge.

- **Units:** `mediaway-<capability>-ffi` (e.g. `mediaway-container-ffi`); unprefixed cores may ship `iso-bmff-ffi` when published; optional `mediaway-common-ffi` for shared C types
- **Umbrella:** additive features (`muxer`, `encoder`, …); **default features empty** so nothing heavy links by accident
- **Style:** opaque handles, explicit error codes, no unwinding across FFI; `extern "C"` only in `*-ffi` crates
- **Coverage:** start with one capability after Rust surface exists; pre-1.0 ABI may break

## Alternatives Considered

| Alternative | Why not |
|-------------|---------|
| No FFI; Rust-only | Blocks many host languages |
| `extern "C"` inside core crates | Pollutes cores; mixes ABI with Rust API |
| Single fat `mediaway-ffi` only | Forces large link graphs on slim hosts |

## Consequences

- Hosts pay only for enabled capabilities; more crates/headers/CI feature matrix
